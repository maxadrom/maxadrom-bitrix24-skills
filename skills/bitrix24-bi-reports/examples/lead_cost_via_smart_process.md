# Пример: отчёт «Стоимость лидов через смарт-процесс расходов»

Готовый кейс для скилла `bitrix24-bi-reports`. SQL датасета — в файле `lead_cost_via_smart_process.sql`.

## Постановка

Когда сквозная аналитика Битрикса недоступна (например, протухла интеграция Я.Директа — см. `references/pitfalls.md`) или для тестов на ручных данных — расходы на рекламу можно заводить в отдельном смарт-процессе и стыковать с лидами через CRM-источник.

Связка идёт не через UTM (как в штатной сквозной аналитике), а напрямую через справочник CRM-источников: и лид, и запись расхода ссылаются на один и тот же источник.

## Схема смарт-процесса «Расходы на рекламу»

Тип СП: **Список** (без канбана). Обязательные поля:

| Поле | Тип | Назначение |
|---|---|---|
| Источник | Привязка к справочнику CRM-источников | Связка с `crm_lead.source_id` |
| Дата начала | Дата | Левая граница периода расхода |
| Дата окончания | Дата | Правая граница (включительно, по 23:59:59) |
| Сумма (деньги) | Деньги | Удобный пользовательский ввод с валютой |
| Сумма (число) | Число (DOUBLE) | Заполняется БП из «Сумма (деньги)»; **именно это поле читается в BI** |

**Почему два поля под сумму:** «Деньги» в BI хранятся как строка `"80000.00|RUB"` (требует парсинга), «Число» — как `DOUBLE` (читается напрямую). Бизнес-процесс копирует значение из первого поля во второе при создании/изменении записи.

## Логика отчёта

1. Каждая запись расхода **раскладывается на дни** периода (`SEQUENCE` + `UNNEST`).
2. Дневной расход = сумма / число дней периода.
3. Если несколько записей по одному источнику пересекаются — дневные расходы **складываются**.
4. Лиды стыкуются с источниками через `crm_lead.source_id = CAST(crm_dynamic_items_NNNN.source_id AS VARCHAR)` (на лиде `source_id` — VARCHAR с префиксом, в СП — BIGINT, кастовать).
5. Фильтр по дате режет **обе стороны**: и расход (по дням), и лидов (по `date_create`).

## Метрики отчёта

- **Расход** — суммарный расход по источнику за период.
- **Лид** — количество лидов источника за период.
- **Цена Л** — расход / число лидов (стоимость лида).
- **Лид успешный** — лиды со `status_semantic_id = 'S'`.
- **Цена УЛ** — расход / число успешных лидов (стоимость успешного лида).

## Портально-специфичные значения

В SQL есть два места, которые **обязательно** уточняются разведкой (см. `references/recon.md`):

- `crm_dynamic_items_1036` — `1036` это `typeId` смарт-процесса расходов конкретного портала. Узнаётся через `SHOW TABLES IN bitrix24 LIKE 'crm_dynamic_items_%'` или `SELECT * FROM bitrix24.crm_smart_proc`.
- `uf_crm_19_datestart`, `uf_crm_19_datestop`, `uf_crm_19_rashoddouble` — кодовые имена кастомных полей конкретного портала. Узнаются через `SELECT * FROM bitrix24.crm_dynamic_items_<typeId> LIMIT 1`.

⚠️ Поля `uf_crm_19_*` в примере уже обёрнуты в `CAST`, потому что пользовательские поля смарт-процессов в BI часто приходят `VARCHAR`'ом даже при типе «Дата»/«Число» в UI (см. `references/pitfalls.md`).

## Шаги настройки в Superset

1. Сохранить SQL (`lead_cost_via_smart_process.sql`) как виртуальный датасет — кнопка «Сохранить и исследовать».
2. Открыть редактирование датасета → вкладка «Столбцы» → нажать «**Синхронизировать столбцы из источника**» (иначе вычисленная колонка `date_create` не появится).
3. В чарте: Time Column = `date_create`, Time Range = «Этот месяц».
4. Колонки чарта в нужном порядке: Источник, Расход, Лид, Цена Л, Лид успешный, Цена УЛ.

Подробнее про Jinja-фильтр и Time Column — `references/jinja-superset.md`.
