# Разведка портала

Часть скилла `bitrix24-bi-reports`. Технические детали шага 3 «Сценария работы над отчётом».

## Зачем нужна разведка — и зачем НЕ нужна

**Список таблиц BI Битрикс24 одинаков на всех порталах** (см. шапку `references/datasets-catalog.md`), поэтому разведка нужна **не** для того, чтобы «узнать, какие таблицы вообще есть», а для трёх конкретных целей:

1. **Пользовательские поля (`_uf`-таблицы).** Набор колонок в `crm_deal_uf`, `crm_lead_uf`, `task_uf`, `crm_contact_uf`, `crm_company_uf`, `crm_quote_uf`, а также в `crm_dynamic_items_<typeId>` (смарт-процессы) зависит от настроек портала.
2. **Конкретные коды и значения.** Стадии (`stage_id`, `status_id`), источники (`source_id`), типы (`type_id` смарт-процессов), категории/воронки (`category_id`) — это значения данных, не структура. На каждом портале они свои.
3. **Заполненность и форматы полей.** Стандартные поля бывают NULL или содержат не то, что можно предположить по имени (типовой пример: `record_duration` в `telephony_call` — длительность файла записи, а не разговора).

⚠️ `SHOW TABLES` ради списка таблиц — **лишний шаг**: набор таблиц одинаков на всех порталах, ориентируйся на каталог. `SHOW TABLES` оправдан только в одном случае — узнать `typeId` смарт-процессов портала (`SHOW TABLES IN bitrix24 LIKE 'crm_dynamic_items_%'`).

## Базовая разведка

`SELECT *` по одной записи, чтобы увидеть реальный набор полей и форматы:

```sql
SELECT * FROM bitrix24.crm_deal LIMIT 1;
SELECT * FROM bitrix24.task WHERE ID = <известный_id>;
```

Разведка идёт пошагово — **по одному SELECT за сообщение** (правило 1). Только после того, как реальная структура подтверждена, писать финальный SQL.

## Что именно проверять

- **Пользовательские поля** в `_uf`-таблицах и в `crm_dynamic_items_<typeId>` — какие `uf_*`/`uf_crm_*` колонки есть и что в них.
- **Типы пользовательских полей.** `uf_crm_*` в BI часто приходят `VARCHAR`'ом, даже если в UI это «Дата» или «Число» (см. `references/pitfalls.md`). Проверка: `SELECT typeof(uf_crm_NN_xxx) FROM ... LIMIT 1`.
- **Конкретные коды/значения** — стадии, источники, ID смарт-процессов, категории/воронки. `SELECT DISTINCT <код>, <название> FROM ...`.
- **Форматы и заполненность** стандартных полей — особенно длительностей, дат, телефонов.

## Доменные мини-чеклисты разведки

- Телефония — мини-чеклист в `references/telephony.md` (типы звонков, живое поле длительности, привязка к сущности).
- Смарт-процессы — мини-чеклист в `references/smart-processes.md` (список типов, структура элементов, воронки, стадии).

## Под «разведкой» в шаге 3 имеется в виду

- проверка пользовательских полей в `_uf`-таблицах;
- проверка конкретных кодов/значений (стадий, источников, ID смарт-процессов);
- проверка форматов и типов данных (особенно `uf_crm_*`, которые часто приходят VARCHAR'ом — см. `references/pitfalls.md`).

**Не имеется в виду:** `SHOW TABLES` ради списка таблиц — он одинаков на всех порталах, этот шаг лишний.
